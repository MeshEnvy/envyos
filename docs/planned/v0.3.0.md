## Multi-volume filesystem CLI naming

**Flagged:** 2026-08-19 (operator)

### Problem

Companion serial debug CLI uses product-style path prefixes:

- `UserData/` → primary `InternalFS` (`_fs`)
- `ExtraFS/` → optional secondary volume (`_fsExtra`: internal `CustomLFS` at `0xD4000` or QSPI)

Repeaters mount **one** filesystem (`InternalFS` only). ExtraFS is companion-only; repeaters reclaim that flash band for OTA staging (`MOTA_STAGE_CEILING=0xED000`).

The virtual-root idea (one namespace spanning volumes) is useful. The `UserData` / `ExtraFS` labels feel arbitrary compared to indexed or mount-point names (`int0` / `int1`, `if0` / `if1`, etc.).

### Current surface

| Build | FS ops | Volume labels |
|-------|--------|---------------|
| Companion (serial debug) | `ls`, `cat`, `rm`, `erase` | `UserData/`, `ExtraFS/` |
| Repeater (`CommonCLI`) | `doctor ls\|stat\|dump\|probe\|check\|gc` | none (single InternalFS) |

There is no general `cp`, `mv`, or `mkdir` CLI today.

### Open design questions

1. **Naming** — indexed (`int0`, `int1`) vs interface ids (`if0`, `if1`) vs explicit mount names.
2. **Scope** — rename companion CLI prefixes only, or unify repeater `doctor` under the same virtual root?
3. **Single-volume builds** — omit prefix, default volume, or always require `int0/`?
4. **Depth** — thin path-prefix layer vs fuller VFS with mount table and cross-volume ops.

No implementation until v0.3.0 scope is chosen.

### Code touchpoints (companion)

- `envycore/examples/companion_radio/MyMesh.cpp` — `ls` / `cat` / `rm` path parsing
- `envycore/examples/companion_radio/DataStore.h` — `_fs`, `_fsExtra`, `_getContactsChannelsFS()`
- `envycore/examples/companion_radio/main.cpp` — `InternalFS` + optional `ExtraFS` / `QSPIFlash`

### Related (already flagged v0.3.0)

- Remove OTA self-serve code (`OTA_SELF_SERVE`, `ota_serve_self`) — see `CHANGELOG.md` Unreleased.

## OTA protocol and CLI (field fleet)

**Flagged:** 2026-08-20 (operator; deferred from v0.2.0 to preserve wire compatibility)

v0.2.0 ships **peer slim repeaters + companions** and **target-only listener catalog filtering** (no wire change). Bench USB relay is **`wismesh-tag-repeater` only** (`OTA_FOLDER_SERIAL`; field slim builds omit folder-relay code). The following need a coordinated v0.3.0 design.

### 1. `OTA_QUERY` v2 — `filter_target` + `filter_base_hash`

**Problem:** v0.2.0 QUERY carries `filter_target` only (12 B payload). Responders filter HAVE rows by
target before the 12-slot serve cap, but **not** by delta base. **Cache** nodes (captured deltas on
SD/NOR) and **relay** nodes (`OTA_FOLDER_SERIAL` + `ota folder on` / motatool folder) still reply with
every matching-target row they hold; peers cannot ask “deltas for *my* target *and* my running
`body_hash`” in one round trip. Listener-side catalog filtering (v0.2.0) and promiscuous cache ingest
do not fix responder-side truncation when a source holds many targets or many delta variants (common
for multi-slug motatool folders on relays).

**Proposed:** extend `OTA_QUERY` with optional trailing `filter_base_hash[8]` (20 B total). Semantics:

| Field | Value | Responder filters HAVE rows to |
|-------|-------|----------------------------------|
| `filter_target` | `0` | all targets (promiscuous / cache capture) |
| `filter_target` | non-zero | that target only (unchanged v0.2.0) |
| `filter_base_hash` | absent or all-zero | any codec / base (FULL + all deltas) |
| `filter_base_hash` | non-zero | FULL (`base_hash` zero in row) **or** delta with matching `base_hash` |

**Backward compatibility:** wire layout is additive. v0.2.0 and older nodes send the 12 B QUERY; v0.3.0
responders parse only what they know and behave exactly as today. v0.3.0 askers append `filter_base_hash`
when EndF identity is known; v0.3.0 responders on old 12 B QUERY ignore base filtering. No protocol
version byte required if length implies capability (12 B vs 20 B). Mixed fleet: old HAVE rows (16 B) and
new HAVE rows (24 B, §2 below) unchanged for this item.

**Primary win:** **cache and relay** nodes answer QUERY with **relevant** `OTA_HAVE` rows only (target
+ applicable delta base), improving hit rate under `OTA_MAX_SERVE` without promiscuous catalog bloat on
peers.

**Code touchpoints:** `OtaProtocol.h`, `OtaManager.cpp` (`handleQuery`, query scheduling from peers),
`ota_protocol.md`, native tests.

### 2. `OTA_HAVE` HaveRow v2 — delta `base_hash` in catalog rows

**Problem:** listeners cannot tell from a 16-byte HaveRow whether a delta applies to their running firmware.
`base_hash` lives only in the manifest (fetched on commit). Wrong-base deltas clutter `ota ls` and force
manifest fetches that fail at apply.

**Proposed:** extend HaveRow to 24 B: add `base_hash[8]` (zero for FULL). Seeders populate from manifest
`base_hash` / running EndF. Listeners filter: own/`ota want` target **and** (FULL or `base_hash ==
EndF.body_hash`). Pairs with §1 QUERY filtering (responder pre-filters; listener still validates on
overheard HAVE). Requires mixed-fleet rules (old nodes ignore extra bytes; new nodes tolerate 16 B rows).

**Code touchpoints:** `OtaProtocol.h`, `OtaManager.cpp` (`handleQuery` / `handleHave`), `ota_protocol.md`,
native tests.

### 3. Direct `ota pull <mid>` without catalog

**Problem:** `OtaCli.cpp` only calls `pull(mid)` when the mid is already in `_catalog`. The engine supports
`OTA_GET_MANIFEST` without a prior HAVE row; operators with a known mid (e.g. from motatool `DESCRIBE` or
release notes) cannot pull directly.

**Proposed:** `ota pull <hex-mid> [flash]` accepts mid from argv, skips catalog lookup, uses
`OtaManager::pull()`. Optional: `ota pull` by manifest hash alias if we add human-readable ids.

**Code touchpoints:** `OtaCli.cpp`, CLI docs, bench test.

### 4. Fleet seeder capacity (related, may ship independently)

**Problem:** `OTA_MAX_SERVE = 12` on tag firmware hides deltas when motatool serves a large folder;
`filter_target` on QUERY helps listeners but does not fix seeder-side truncation.

**Proposed:** raise `OTA_MAX_SERVE` / catalog caps where RAM allows; motatool fleet-priority sort
(applicable delta for asker's target first). May be v0.2.x bench fix if RAM budget allows without wire change.

### Missing information

| Question | Blocks |
|----------|--------|
| Implicit QUERY length negotiation (12 B vs 20 B) vs explicit version byte? | Wire spec + mixed fleet |
| Minimum fleet fraction on v0.3.0 before enabling 20 B QUERY emit / 24 B HAVE emit? | Rollout policy |
| Tag RAM headroom for `OTA_MAX_SERVE` > 12? | Seeder capacity item |

### Related (already flagged v0.3.0)

- Remove OTA self-serve code (`OTA_SELF_SERVE`, `ota_serve_self`) — see `CHANGELOG.md` Unreleased.

## OTA cache role (deferred from v0.2.0)

**Flagged:** 2026-08-21 (operator; none deployed; ship v0.2.0 as peer-only first)

### Problem

Field repeaters need a **delta warehouse** without a tethered laptop. Storage media varies by board (RAK15002 SD, SenseCAP onboard QSPI NOR, future SPI flash, etc.). Cache code + PIO envs exist in-tree but are **not** in `scripts/targets.txt` until the first cache wave ships.

### Design (settled 2026-08-21): role mixin × storage medium

Cache is an **abstract role** (promiscuous capture + serve of deltas) that requires a **concrete
bulk-storage capability** only some boards have (SD hat, onboard QSPI NOR, future SPI flash, ...).
PlatformIO has single-chain inheritance, so the role is a **flag mixin** and the medium stays in the
concrete env name:

| Piece | Pattern | Examples |
|-------|---------|----------|
| Base | `*_repeater_slim` | unchanged |
| Storage capability (PIO env: medium driver + `OTA_SEEDER_STORAGE_<medium>`) | `<Board>_storage_<medium>` | `RAK_4631_storage_sd`, `SenseCap_Solar_storage_qspi` |
| Role mixin (root `platformio.ini`, medium-agnostic) | `[ota_cache]` | `-D OTA_SEEDER_CACHE` + `-UOTA_FOLDER_SERIAL` |
| Concrete cache env = storage env + mixin | `<Board>_cache_<medium>` | `RAK_4631_cache_sd`, `SenseCap_Solar_cache_qspi` |
| Shipped slug | `<board>-cache-<medium>` | `rak4631-cache-sd`, `sensecap-p1pro-cache-qspi` |

Firmware mirrors the split: `SeederFs.h` abstracts the FS and `#error`s without a concrete
`OTA_SEEDER_STORAGE_SD|_QSPI` backend; `CacheSeeder.h` `#error`s if `OTA_SEEDER_CACHE` is set without
`OTA_SEEDER_STORAGE`. Adding a medium = new `SeederFs` backend + `*_storage_<medium>` env + one
`*_cache_<medium>` env reusing the mixin. No generic `*-cache` slug — mediums differ in BOM, bring-up,
and `target_id`. **Do not** conflate bench USB relay with cache: relay = `OTA_FOLDER_SERIAL` on
`wismesh-tag-repeater`; cache = external FS capture + serve.

### Code already in-tree (not built for v0.2.0 publish)

- `CacheSeeder.*`, `OTA_SEEDER_*` flags, allowlist CLI (`ota cache allow`)
- PIO: `RAK_4631_cache_sd`, `SenseCap_Solar_cache_qspi` (+ `_storage_<medium>` parents, `[ota_cache]` mixin) — add to `targets.txt` when v0.3.0 ships

### Missing information

| Question | Blocks |
|----------|--------|
| Which storage mediums ship in first cache wave? | targets.txt rows |
| Cache + relay on same board ever needed? | `[ota_cache]` unsets `OTA_FOLDER_SERIAL` today |

## Remote EnvyBoot OTA (dual updates)

**Flagged:** 2026-08-21 (operator)

### Problem

nRF52 firmware OTA is **one-directional today**: the running app stages and approves a `.mota`, then
reboots; EnvyBoot applies an in-place delta over the **app region** only (`ota_protocol.md` §12).
Bootloader updates require USB (UF2 drag-and-drop or recovery zip). Fleet on distro **v0.1.2** still
ships EnvyBoot **0.1.2** while dev carries **0.2.0** (WDT feed, mota ABI). The firmware apply gate
already refuses deltas when the bootloader is too old (`OtaApply.cpp`: "update the bootloader first").

Field repeaters cannot pick up EnvyBoot fixes over LoRa without a site visit.

### Proposed (symmetric handoff)

Mirror the existing app OTA choreography with the **bootloader as apply target**:

1. Firmware stages a **bootloader-target** signed `.mota` in flash (same staging band below InternalFS).
2. Operator or policy writes `APRV` and sets a new GPREGRET magic (e.g. `GPREGRET_OTA_BL_APPLY`, distinct
   from app apply `0x6A`).
3. On reboot, EnvyBoot applies the in-place delta over `[MOTA_NRF52_BL_START, MOTA_NRF52_BL_END)` (~39 KB),
   verifies `image_hash`, then boots the app (optionally chain into a staged app-target mota in the same boot).

The running firmware **does not** erase the bootloader region directly. Same safety model as app OTA:
verify fully before commit; destructive apply only from the bootloader path. USB recovery zip remains
break-glass if power fails mid-BL write.

**Not in scope for v0.3.0 initial ship:** firmware-side NVMC writes into the BL region while the app is
running (higher brick risk; no verify-before-commit boundary).

### Design pieces

| Piece | Today | Bootloader OTA |
|-------|-------|----------------|
| Apply target | App `[APP_BASE, mota_start)` | BL `[BL_START, mota_start)` |
| Base identity | Running firmware `EndF.body_hash` | Hash of current BL image region (or embedded BL identity marker) |
| `target_id` / manifest flag | Per PlatformIO env (firmware role) | Per-board BL target id or `apply_target=bootloader` flag |
| motatool | `--patch-type in-place` for app hex | `--target bootloader` (or equivalent) against extracted BL hex |
| Apply order | One mota per reboot | **BL before FW** when existing ABI gate fires; optional dual staged motas |

### Hard parts

- **Self-apply:** bootloader executes from flash while rewriting that region. Likely needs apply loop
  copied to RAM (reference: UF2 `ghostfat.c` bootloader update path).
- **Brick class:** BL failure leaves no mota-apply path; recovery zip + serial DFU required. Document in
  release notes and operator guide.
- **Version skew:** extend `MOTABLDR` capability marker or parallel ABI for BL-target motas; gate BL
  apply the same way firmware gates on `apply_abi` / codec mask today.

### Primary win

Remote EnvyBoot upgrades (0.1.2 → 0.2.0+ WDT feed, future OTAFIX fixes) without climbing every
repeater for UF2. Pairs with firmware OTA for true "dual updates" on a mixed fleet.

### Code touchpoints

- `bootloader/src/ota_delta.c` — BL-target apply path (+ RAM stub if needed)
- `bootloader/src/ota_layout.h` — new GPREGRET magic (document occupancy table)
- `envycore/src/helpers/ota/OtaApply.cpp` — stage/approve BL mota; `ota applybootloader` or unified CLI
- `envycore/src/helpers/ota/OtaFlashLayout_nrf52.h` — BL apply geometry checks
- `motatool/` — pack/verify BL-target in-place deltas
- `envycore/docs/ota_protocol.md` — manifest target discriminator + apply contract

### Missing information

| Question | Blocks |
|----------|--------|
| BL base identity: raw region hash vs embedded EnvyBoot trailer? | motatool base + device gate |
| Single boot: BL apply then app apply, or always two reboots? | Operator workflow |
| Minimum BL version that can self-apply (bootstrap from 0.1.x)? | Fleet rollout from v0.1.2 |
| Full BL image (~39 KB) vs delta over LoRa for rare updates? | motatool publish matrix |

No implementation until v0.3.0 scope is chosen.

## Companion InternalFS wedge mitigation

**Deferred:** 2026-08-19 (operator; ship with v0.3.0, not v0.2.0)

### Problem

WisMesh Tag **companion BLE** puts prefs, identity, contacts, channels, and adv blobs on **one** 28 KB InternalFS (`EXTRAFS=1` not enabled; RAK4631 companion splits contacts onto ~100 KB ExtraFS). Heavy mesh use can fill the partition; saves fail like repeater wedge cases, but there is no `doctor` CLI and no USB on the BLE build for recovery.

Repeaters got flat `doctor stat|gc|check` + atomic prefs in v0.2.0. Companions got atomic saves + boot fsck only.

### Planned (v0.3.0)

1. **`EXTRAFS=1` on WisMesh companion** — `variants/rak_wismesh_tag/platformio.ini` companion envs; linker already uses `nrf52840_s140_v6_extrafs.ld`.
2. **`doctor check` / `doctor gc` on companion** — wire through companion serial debug path (USB variant first); optional parity with repeater `stat`/`ls` under virtual-root naming.
3. **Packet log cap** (if still open) — repeater `log start` uncapped growth; less relevant to companion but same InternalFS class.

Tie to **multi-volume FS CLI naming** above when choosing command surface.

### Code touchpoints

- `envycore/variants/rak_wismesh_tag/platformio.ini` — `-D EXTRAFS=1` on companion envs
- `envycore/examples/companion_radio/main.cpp` — `DataStore(InternalFS, ExtraFS, …)` already gated on `EXTRAFS`
- `envycore/examples/companion_radio/MyMesh.cpp` — serial debug CLI (not `CommonCLI` today)
- `envycore/docs/envyos_cli_extensions.md` — operator doc

No implementation until v0.3.0.

## LFSv2 + chunked contacts (upstream [#2964](https://github.com/meshcore-dev/MeshCore/pull/2964))

**Flagged:** 2026-08-20 (maintainer feedback on [#3254](https://github.com/meshcore-dev/MeshCore/pull/3254))

### Context from upstream

MeshEnvy opened [#3254](https://github.com/meshcore-dev/MeshCore/pull/3254) (atomic write-rename for prefs, ACL, regions, adv blobs). Maintainers [@liamcottle](https://github.com/liamcottle) and [@oltaco](https://github.com/oltaco) responded:

- Atomic rename **does not fix nRF LittleFS corruption**. Root cause is **block size (128 B) vs page erase (4 kB)** on Adafruit LittleFS v1: power loss during a write can erase more flash than LittleFS metadata pairs expect, corrupting or losing files even with tmp+rename.
- The real fix is oltaco's draft [#2964](https://github.com/meshcore-dev/MeshCore/pull/2964): **LittleFS v2**, **4 kB blocks on ExtraFS**, **chunked contacts** (~4 kB per contact update), atomic writes throughout, identity/prefs migrated to storage FS with UserData backup.
- Repro: full contacts list + incoming advert + power cycle during write → corruption every time on T1000e-class boards (oltaco, Aug 6 thread on #2964).

EnvyOS **already ships** write-rename on `envyos/main` (commit `f79f12d1`, v0.2.0): `ConfigSerializer::writeFileAtomic` covers repeater prefs, ACL, regions, and companion prefs/contacts/channels/blobs. Upstream [#3254](https://github.com/meshcore-dev/MeshCore/pull/3254) is the **pure extraction** of that work for meshcore-dev; it is not pending integration here.

**#3254 is not redundant with #2964.** They fix different layers:

| Layer | #3254 (write-rename) | #2964 (LFSv2) |
|-------|----------------------|---------------|
| Crash mid-write leaves truncated file | Fixes (old file intact until rename) | Partial — only where oltaco wired tmp+rename |
| nRF metadata corruption on power loss | Does **not** fix (128 B block vs 4 kB erase) | Fixes (LFSv2 + 4 kB blocks) |

#2964 atomic coverage (verified on branch): companion `IdentityStore`, `DataStore` prefs/contacts/channels. **Still truncate-then-write on #2964:** repeater `CommonCLI` prefs (`fs->remove` then open), `ClientACL`, `RegionMap`, companion `adv_blobs`. #3254 covers those repeater paths plus shared `ConfigSerializer::writeFileAtomic`.

For v0.3.0: merge **#2964** onto `envyos/main` (atomic saves already there); port `writeFileAtomic` onto oltaco's new `DataStore`/`storageFS` layout where his branch still uses truncate-write. Upstream #3254 stays open as the meshcore-dev extraction.

### What #2964 changes (oltaco branch `lfs2-chunked-contacts`)

| Area | Change |
|------|--------|
| Filesystem | LFSv1 → LFSv2 everywhere; ExtraFS reformats to 4 kB blocks |
| Contacts | Monolithic file → per-contact chunks (single-block writes) |
| Identity / prefs | Move to ExtraFS/QSPI `storageFS`; backup copy on UserData |
| adv_blobs | Not migrated on ExtraFS reformat (ephemeral); `MAX_BLOBRECS` 100 → 40 |
| Writes | Atomic tmp+rename in `DataStore`, `IdentityStore`, channels |
| Migration | One-time first boot; **rolling back to non-LFSv2 firmware wipes FS** |

Tested on multiple nRF boards (T1000e, T114, Xiao, WioTrackerL1); limited ESP32/RP2040/STM32. Still draft; oltaco planned Aug 10 rebase on current `dev`.

### v0.3.0 incorporation plan

**Prerequisite:** ship **v0.2.0** first (in progress). LFSv2 is a **one-way fleet migration** — not a v0.2.0 hotfix.

1. **Track upstream** — watch #2964 rebase/merge on `meshcore-dev/dev`; bench on RAK4631 slim repeater + WisMesh companion + SenseCAP when oltaco pushes.
2. **Keep #3254 open upstream** — extraction of work already on `envyos/main`; note in PR thread it complements #2964. After #2964 merge locally, rebase `feature/atomic-fs-save` / #3253 / #3252 if needed.
3. **Integration branch** — after v0.2.0 tag: `feature/lfsv2-chunked-contacts` from latest `meshcore/pr-2964`, merge `envyos/main`, resolve conflicts, rebuild all `targets.txt` slugs.
4. **Bench matrix (blocking field OTA to v0.3.0)**
   - First-boot migration from v0.2.0 nodes (prefs, identity, contacts intact)
   - Power-loss during contact write (oltaco repro procedure)
   - Power-loss during prefs save from app
   - Repeater `doctor stat|gc|check` on LFSv2 InternalFS
   - LoRa OTA apply to v0.3.0 on EnvyBoot 0.2.0+
   - Downgrade attempt → confirm FS wipe / expected failure mode
5. **Fleet policy** — export contacts/identity before v0.3.0 OTA; document one-way migration in release notes + blog; tie to companion `EXTRAFS=1` work below (LFSv2 moves prefs to storage FS — aligns with splitting WisMesh companion off 28 KB InternalFS).
6. **GUCP** — #3254 stays `submitted` (complementary); #2964 tracked as upstream dependency to consume; doctor / FS errors stay `submitted`.

### Relationship to other v0.3.0 items
