## Multi-volume filesystem CLI naming

**Flagged:** 2026-08-19 (operator)

### Problem

Companion serial debug CLI uses product-style path prefixes:

- `UserData/` → primary `InternalFS` (`_fs`)
- `ExtraFS/` → optional secondary volume (`_fsExtra`: internal `CustomLFS` at `0xD4000` or QSPI)

Repeaters mount **one** filesystem (`InternalFS` only). ExtraFS is companion-only; repeaters reclaim that flash band for OTA staging (`MOTA_STAGE_CEILING=0xED000`).

The virtual-root idea (one namespace spanning volumes) is useful. The `UserData` / `ExtraFS` labels feel arbitrary compared to indexed or mount-point names (`int0` / `int1`, `if0` / `if1`, etc.).

### Current surface

| Build | FS ops | Volume labels |
|-------|--------|---------------|
| Companion (serial debug) | `ls`, `cat`, `rm`, `erase` | `UserData/`, `ExtraFS/` |
| Repeater (`CommonCLI`) | `doctor ls\|stat\|dump\|probe\|check\|gc` | none (single InternalFS) |

There is no general `cp`, `mv`, or `mkdir` CLI today.

### Open design questions

1. **Naming** — indexed (`int0`, `int1`) vs interface ids (`if0`, `if1`) vs explicit mount names.
2. **Scope** — rename companion CLI prefixes only, or unify repeater `doctor` under the same virtual root?
3. **Single-volume builds** — omit prefix, default volume, or always require `int0/`?
4. **Depth** — thin path-prefix layer vs fuller VFS with mount table and cross-volume ops.

No implementation until v0.3.0 scope is chosen.

### Code touchpoints (companion)

- `envycore/examples/companion_radio/MyMesh.cpp` — `ls` / `cat` / `rm` path parsing
- `envycore/examples/companion_radio/DataStore.h` — `_fs`, `_fsExtra`, `_getContactsChannelsFS()`
- `envycore/examples/companion_radio/main.cpp` — `InternalFS` + optional `ExtraFS` / `QSPIFlash`

### Related (already flagged v0.3.0)

- Remove OTA self-serve code (`OTA_SELF_SERVE`, `ota_serve_self`) — see `CHANGELOG.md` Unreleased.

## Companion InternalFS wedge mitigation

**Deferred:** 2026-08-19 (operator; ship with v0.3.0, not v0.2.0)

### Problem

WisMesh Tag **companion BLE** puts prefs, identity, contacts, channels, and adv blobs on **one** 28 KB InternalFS (`EXTRAFS=1` not enabled; RAK4631 companion splits contacts onto ~100 KB ExtraFS). Heavy mesh use can fill the partition; saves fail like repeater wedge cases, but there is no `doctor` CLI and no USB on the BLE build for recovery.

Repeaters got flat `doctor stat|gc|check` + atomic prefs in v0.2.0. Companions got atomic saves + boot fsck only.

### Planned (v0.3.0)

1. **`EXTRAFS=1` on WisMesh companion** — `variants/rak_wismesh_tag/platformio.ini` companion envs; linker already uses `nrf52840_s140_v6_extrafs.ld`.
2. **`doctor check` / `doctor gc` on companion** — wire through companion serial debug path (USB variant first); optional parity with repeater `stat`/`ls` under virtual-root naming.
3. **Packet log cap** (if still open) — repeater `log start` uncapped growth; less relevant to companion but same InternalFS class.

Tie to **multi-volume FS CLI naming** above when choosing command surface.

### Code touchpoints

- `envycore/variants/rak_wismesh_tag/platformio.ini` — `-D EXTRAFS=1` on companion envs
- `envycore/examples/companion_radio/main.cpp` — `DataStore(InternalFS, ExtraFS, …)` already gated on `EXTRAFS`
- `envycore/examples/companion_radio/MyMesh.cpp` — serial debug CLI (not `CommonCLI` today)
- `envycore/docs/envyos_cli_extensions.md` — operator doc

No implementation until v0.3.0.

## LFSv2 + chunked contacts (upstream [#2964](https://github.com/meshcore-dev/MeshCore/pull/2964))

**Flagged:** 2026-08-20 (maintainer feedback on [#3254](https://github.com/meshcore-dev/MeshCore/pull/3254))

### Context from upstream

MeshEnvy opened [#3254](https://github.com/meshcore-dev/MeshCore/pull/3254) (atomic write-rename for prefs, ACL, regions, adv blobs). Maintainers [@liamcottle](https://github.com/liamcottle) and [@oltaco](https://github.com/oltaco) responded:

- Atomic rename **does not fix nRF LittleFS corruption**. Root cause is **block size (128 B) vs page erase (4 kB)** on Adafruit LittleFS v1: power loss during a write can erase more flash than LittleFS metadata pairs expect, corrupting or losing files even with tmp+rename.
- The real fix is oltaco's draft [#2964](https://github.com/meshcore-dev/MeshCore/pull/2964): **LittleFS v2**, **4 kB blocks on ExtraFS**, **chunked contacts** (~4 kB per contact update), atomic writes throughout, identity/prefs migrated to storage FS with UserData backup.
- Repro: full contacts list + incoming advert + power cycle during write → corruption every time on T1000e-class boards (oltaco, Aug 6 thread on #2964).

EnvyOS **already ships** write-rename on `envyos/main` (commit `f79f12d1`, v0.2.0): `ConfigSerializer::writeFileAtomic` covers repeater prefs, ACL, regions, and companion prefs/contacts/channels/blobs. Upstream [#3254](https://github.com/meshcore-dev/MeshCore/pull/3254) is the **pure extraction** of that work for meshcore-dev; it is not pending integration here.

**#3254 is not redundant with #2964.** They fix different layers:

| Layer | #3254 (write-rename) | #2964 (LFSv2) |
|-------|----------------------|---------------|
| Crash mid-write leaves truncated file | Fixes (old file intact until rename) | Partial — only where oltaco wired tmp+rename |
| nRF metadata corruption on power loss | Does **not** fix (128 B block vs 4 kB erase) | Fixes (LFSv2 + 4 kB blocks) |

#2964 atomic coverage (verified on branch): companion `IdentityStore`, `DataStore` prefs/contacts/channels. **Still truncate-then-write on #2964:** repeater `CommonCLI` prefs (`fs->remove` then open), `ClientACL`, `RegionMap`, companion `adv_blobs`. #3254 covers those repeater paths plus shared `ConfigSerializer::writeFileAtomic`.

For v0.3.0: merge **#2964** onto `envyos/main` (atomic saves already there); port `writeFileAtomic` onto oltaco's new `DataStore`/`storageFS` layout where his branch still uses truncate-write. Upstream #3254 stays open as the meshcore-dev extraction.

### What #2964 changes (oltaco branch `lfs2-chunked-contacts`)

| Area | Change |
|------|--------|
| Filesystem | LFSv1 → LFSv2 everywhere; ExtraFS reformats to 4 kB blocks |
| Contacts | Monolithic file → per-contact chunks (single-block writes) |
| Identity / prefs | Move to ExtraFS/QSPI `storageFS`; backup copy on UserData |
| adv_blobs | Not migrated on ExtraFS reformat (ephemeral); `MAX_BLOBRECS` 100 → 40 |
| Writes | Atomic tmp+rename in `DataStore`, `IdentityStore`, channels |
| Migration | One-time first boot; **rolling back to non-LFSv2 firmware wipes FS** |

Tested on multiple nRF boards (T1000e, T114, Xiao, WioTrackerL1); limited ESP32/RP2040/STM32. Still draft; oltaco planned Aug 10 rebase on current `dev`.

### v0.3.0 incorporation plan

**Prerequisite:** ship **v0.2.0** first (in progress). LFSv2 is a **one-way fleet migration** — not a v0.2.0 hotfix.

1. **Track upstream** — watch #2964 rebase/merge on `meshcore-dev/dev`; bench on RAK4631 slim repeater + WisMesh companion + SenseCAP when oltaco pushes.
2. **Keep #3254 open upstream** — extraction of work already on `envyos/main`; note in PR thread it complements #2964. After #2964 merge locally, rebase `feature/atomic-fs-save` / #3253 / #3252 if needed.
3. **Integration branch** — after v0.2.0 tag: `feature/lfsv2-chunked-contacts` from latest `meshcore/pr-2964`, merge `envyos/main`, resolve conflicts, rebuild all `targets.txt` slugs.
4. **Bench matrix (blocking field OTA to v0.3.0)**
   - First-boot migration from v0.2.0 nodes (prefs, identity, contacts intact)
   - Power-loss during contact write (oltaco repro procedure)
   - Power-loss during prefs save from app
   - Repeater `doctor stat|gc|check` on LFSv2 InternalFS
   - LoRa OTA apply to v0.3.0 on EnvyBoot 0.2.0+
   - Downgrade attempt → confirm FS wipe / expected failure mode
5. **Fleet policy** — export contacts/identity before v0.3.0 OTA; document one-way migration in release notes + blog; tie to companion `EXTRAFS=1` work below (LFSv2 moves prefs to storage FS — aligns with splitting WisMesh companion off 28 KB InternalFS).
6. **GUCP** — #3254 stays `submitted` (complementary); #2964 tracked as upstream dependency to consume; doctor / FS errors stay `submitted`.

### Relationship to other v0.3.0 items

- **Multi-volume FS CLI naming** — #2964 renames `_getContactsChannelsFS()` → `storageFS` and moves prefs/identity there. Virtual-root naming (`int0`/`int1`) should target the post-LFSv2 layout, not pre-migration `UserData`/`ExtraFS` labels.
- **Companion InternalFS wedge** — chunked contacts + 4 kB atomic writes reduce whole-file rewrite pressure; `EXTRAFS=1` on WisMesh still planned for capacity, but durability root fix is LFSv2.
